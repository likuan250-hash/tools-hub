# 代码评审清单（Code Review Checklist）

评审他人 PR 时，除了"代码看起来对"，重点盯这几类**小团队最容易翻车**的点。问题不在写不写得出来，而在装包/生产环境才暴露。

## 1. 构建与产物（最高优先级）
- 新增了静态资源（css/js/图片/html/字体）？它的目录是否加进了 `package.json` 的 `build.files`？
  - ⚠️ 漏打包是这类项目最常见的发布事故（本次全黑的根因）。
- 新增了 `@import` / 外部资源引用？确认它在**装包后**依然可达（`@import "../shared"` 在 asar 内不可靠，应走构建期内联，见 `scripts/prepare-build.js`）。
- 改了 `scripts/verify-build-assets.js` 的断言？确认新关键资产也被覆盖；并做一次负向验证（故意缺产物应被拦）。

## 2. 秘钥与配置
- 有没有明文 secret / token / 密码写进代码或文档？
- `.masterkey`、`.env`、凭证是否可能进 git？（已在 `.gitignore`，但新增敏感文件要自觉加进去。）

## 3. 错误处理与健壮性
- 异步操作（Promise / 子进程 / 网络）有没有 `.catch` 或 `try/catch`？失败会不会静默吞掉、导致界面卡死或无提示？
- 子进程（Express 子服务、fork）异常退出有没有看门狗/重启/提示？

## 4. dev / prod 一致性（核心思维转变）
- 作者是否只靠本地 `npm start` 验证？涉及 UI/构建的改动，**必须提醒装包实测**。
- "我机器上是好的" 不等于 "装包能用"——这是本项目的头号风险。

## 5. 测试
- 涉及 `kdocs-tool` 的改动，是否跑了 `npm test`（CI 门禁也会跑）？
- 纯前端/构建改动，是否有最小的手测证据（截图/步骤）？

## 6. 样式与主题
- 新增样式是否使用 `shared/tokens.css` 的 token 变量（如 `--bg-1`、`--text`），**不在别处硬编码颜色**？
- 新增颜色/主题相关改动，是否在明暗两套都验证过可读性（暗色底+黑字是最典型的"看不见"坑）？

## 评审姿态
- 对事不对人，给出可执行的修改建议，而不是只说"不太好"。
- 发现好做法就点名表扬，沉淀进文档/规范，形成正循环。
- 拿不准的，约个 10 分钟结对看一眼，比来回评论高效。
